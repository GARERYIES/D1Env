# D1Env 产品与架构设计

日期：2026-10-06。状态：交付用户审阅的设计；未实现、未接真机。

## 1. 目标、用户与范围

目标用户是实验室新人：不必理解 Docker、ROS launch、DDS 或编辑 YAML，也能把已适配的 D1 开发环境安装并启动到一个可解释的状态。

用户已明确要求：参考 IOENV 底层架构；图形交互选择 D1 版本；尽可能一键部署；先规划，再交给 Codex 分阶段实现。

设计假设：第一版用于个人/实验室本地受信网络；现场有能够确认型号、固件与物理安全条件的操作人员。真实执行主机第一优先 Ubuntu 22.04 x86_64；macOS 可用于开发 UI 和浏览器访问 Linux 主机，不作为首版机器人驱动运行平台。aarch64 是待构建与现场验证的候选，不默认已支持。MaxPro 另做 ABI/运行时验证。

“一键”的承诺范围是：对**已验证组合**自动完成可安全自动化的软件步骤。它不意味着自动插网线、识别任何固件、跳过管理员授权或保证任何机器人插上即走。

## 2. 方案选择

| 路线 | 优点 | 主要缺点 | 选择 |
|---|---|---|---|
| Fork IOENV 并给 Bash 加页面 | 起步快，行为接近参考项目 | 执行型配置、权限较宽、缺少作业状态契约 | 不作产品核心 |
| 独立部署引擎＋Profile＋中文 Web 向导 | CLI/UI 共用逻辑，易测试，兼容性可追溯 | 需要实现小型任务编排器 | **采用** |
| 从完整云端机器人管理平台开始 | 后期多机器人能力强 | 超出单机部署目标，增加账号、网络和运维负担 | 暂不做 |

不改写 SLAM、Nav2 或厂商运控算法，不在控制回路接 LLM，不引入 Kubernetes、账号系统、云数据库或多租户服务。

## 3. 用户流程

### 3.1 首次打开

目标发行形式为经过验证的 Ubuntu 安装包与桌面入口。后端和编译好的静态前端随包交付；Node 仅用于研发构建。用户不需要 pip/npm、Git、编译 ROS 工作区。

初次运行检查 Docker；缺失或权限不足时展示原因、安装来源及所需授权。管理员操作是独立可审查步骤，不能从浏览器随意执行 shell。已有 Docker 不自动覆盖；驱动/内核/固件不自动升级。

发行包和镜像尚未存在，发布前必须由 CI 真实构建并填入真实校验值；开发文档不得伪造下载地址。

### 3.2 五步向导

| 页面 | 用户看到的内容 | 必须处理的条件 |
|---|---|---|
| 使用方式 | 演示体验 / 真实机器人只读部署 | 演示默认；全程显著 MOCK 标识 |
| 机器人配置 | 友好的产品/外形卡片：点足、轮足、MaxPro、“我不确定”；必要时引导确认固件和传感器 | SDK 家族由兼容规则解析，放高级详情；不要求新人理解内部代号，不猜默认硬件配置 |
| 执行电脑 | 实际执行主机 OS/CPU、Docker、磁盘、网卡 | 浏览器所在电脑与执行主机分开显示 |
| 部署预览 | 下载量（可得时）、目录、服务、权限、网络及风险 | 未知尺寸显示未知，不编造；必要授权逐项说明 |
| 运行与结果 | 当前真实步骤、失败原因、重试/取消/恢复/导出 | 进程启动、软件就绪、数据就绪、真机验证分别显示 |

正常路径优先只让用户选择任务、机器人卡片和执行电脑；已有可信配置不重复询问。需要固件证据时，先尝试经确认无副作用的只读查询；不可查询则展示在遥控器/标签何处查看的引导，不假装自动识别完成。所有技术字段保留在高级详情中可核对。

机器人卡片展示能力清单，而非一个含糊“支持”标志。每项能力都有来源、实现状态及验证证据。卡片可以出现 MaxPro，但其未验证功能必须灰显、解释原因。

### 3.3 完成页与错误页

完成页按运行模式显示不同措辞：

- 演示：“演示流程完成（MOCK），未部署真机。”
- 真实软件测试：“软件环境检查通过，未连接真机。”
- 真机只读：“遥测检查通过；运动控制未启用。”

不得只有一个绿色 READY 灯。失败页展示检查项目、观测证据、原因、建议操作和可复制错误码；“取消部署”与“停止运动请求”不是同一个按钮。

## 4. 模块架构

```text
中文 Web 向导 ─┐
              ├→ 同一 Application Service → Profile/兼容解析 → DeploymentPlan
CLI / 诊断 ───┘                              ↓
                                单主机部署引擎＋持久化任务事件
                                  ↓                  ↓
                         受限 Docker 执行器       诊断与报告
                                  ↓
                   CPU 基础 / SDK 只读 / 传感器 / SLAM / Nav2
                                  ↓
                    分型号 D1 高层适配器 → 厂商原生 SDK
                                  ↓
                         保留原厂运控的 D1 本体
```

Web 只管理部署与显示状态，不承担机器人高频控制。后续运动命令网关必须在靠近机器人的执行主机运行，不依赖浏览器标签页继续存活。

### 4.1 技术栈决策

后端 Python 3.10、FastAPI、Pydantic v2、SQLite；CLI Typer；前端 React＋TypeScript＋Vite，构建后作为静态资源交付。运行环境 Docker Engine/Compose v2。ROS 侧以 Humble 作为首个上层目标，适配器使用厂商支持的 C++ 接口。准确包版本在 M0/构建阶段锁定，不凭本文编造 patch 版本。

M0–M2 不依赖 ROS、厂商 SDK 或真实 Docker；真实 Docker 适配器在 M3 实现。后端与前端由同源地址服务，减少不必要的跨域接口。

### 4.2 最小模块契约

| 模块 | 输入 | 输出/职责 |
|---|---|---|
| Catalog | 严格的随包 Profile | 家族、变体、架构、能力、来源、支持证据 |
| Doctor | ExecutionTarget、所选功能 | 带证据的 CheckResult，不修改机器 |
| Resolver | DeploymentRequest＋HostFacts＋Catalog | 可重复的 DeploymentPlan 或具体阻塞项 |
| Job Engine | 已批准的 DeploymentPlan | 可恢复 Job、逐步骤 JobEvent |
| Executor | 已解析的白名单 Operation | OperationResult；不接受任意 shell |
| Diagnostics | 软件探针/ROS 遥测 | 新鲜度、数据来源、UNKNOWN/PASS/FAIL |
| Report | Job＋证据＋去敏配置 | 可离线阅读的 JSON/Markdown 诊断包 |

UI 与 CLI 不复制解析逻辑；两者都调用同一服务。

## 5. Profile 与兼容性模型

Profile 不是可执行脚本。必须拒绝额外字段和可执行 YAML 标签。只加载随发行包提供或显式信任的配置；新手界面不接受任意第三方插件代码。

核心字段：schema_version、profile_id、vendor、sdk_family、variant、architectures、runtime_requirements、firmware_rules、capabilities、sensor_contract、network_requirements、artifact_requirements、evidence_refs。

能力的声明与实现分开：`declared_by_vendor` 不自动变成可用。实现/验证状态为 `not_implemented / documented / implemented / integration_verified / hardware_verified`。各能力独立评定；同一个型号可以只读已验证、导航未实现。

候选家族：`edu_ultra_zsl_1`、`edu_ultra_zsl_1w`、`maxpro_legacy`、`unknown`。商品名称仅作为提示；必须匹配 SDK 家族、实际硬件变体、固件与 CPU。已见文档事实见 [源码调研](../../research/SOURCE_AUDIT.md)。

来源或兼容范围无法确定时：生成被阻塞的计划和诊断，不执行实机安装。不能通过“强制继续”按钮绕过硬件能力缺失。固件版本是 UNKNOWN 时不得启用运动。

生产 ArtifactRef 必须包含实际来源、架构、获取方式及不可变标识。远程镜像使用 registry manifest digest；本地构建候选记录实际 image ID 与构建来源，不把两种标识混淆。无摘要/无产物时，真实执行拒绝；MOCK 工件明确 kind=mock，不能流入 Docker 执行器。

## 6. 部署流程与恢复

部署状态：`PLANNED → PREFLIGHT → ACQUIRING → CONFIGURING → STARTING → VERIFYING → SUCCEEDED`；异常状态：`BLOCKED / FAILED / CANCELLED / INTERRUPTED`。

`SUCCEEDED` 仅说明该计划的声明目标通过验证，必须附 mode 和 verified_scope；它不是“所有机器人功能就绪”。

同一目标最多一个变更作业。Plan ID 是规范化计划内容的 SHA-256，包含 profile/依赖版本与执行目标，不含密钥、会话令牌或探针观测时间。执行前重新检查必要条件。重复请求返回现有作业，不能创建第二套服务；失败后显式重试使用新的幂等键。同一 key 不能绑定不同计划。状态保存在 SQLite；服务重启后先盘点真实资源，不能把数据库里旧的非终态作业当成仍在运行。

每个操作有预条件、超时、可观测结果、资源归属和撤销策略。只有本次创建且可安全撤销的对象能自动清理。地图/bag/用户配置不参与自动删除。回滚软件版本不等于恢复固件或本体配置。

下载进度来自实际事件；已存在缓存要验证摘要。镜像站必须保留预期内容校验，不能关闭 TLS。支持离线工件导入是 M3 后的功能；导入归档需防路径穿越、超大包及符号链接逃逸。

## 7. 诊断分层

| 层次 | 检查 | 不允许的推断 |
|---|---|---|
| 宿主机 | OS/架构、Docker 可访问性、磁盘、网络路由 | 没 GPU 就阻塞 CPU 只读部署 |
| 软件 | 镜像/依赖、进程、生命周期、探针结果 | 容器 running 就算应用 ready |
| 协议 | 数据可解码、型号/版本、实际更新时间 | ping 通就算 SDK 正常 |
| ROS | topic 类型/QoS、时间戳、频率、TF 唯一性 | topic 存在就算传感器正常 |
| 任务 | 所需地图/定位/观测是否可用 | 规划出路径就算导航实机成功 |

每条检查包含 status=`PASS / WARN / FAIL / UNKNOWN / SKIPPED`、observed_at、evidence_source、reason、remediation。健康探针可能使用示例测试阈值，但阈值必须注明为软件测试值，不能冒充厂商安全规格。

## 8. 主机、网络与权限

首版真实运行仅支持经过测试的 Linux 原生执行主机。Mac/Windows 浏览器可访问该主机的回环服务，例如通过用户显式建立的 SSH 隧道；首版不实现跨平台自动远程安装器。浏览器 UI 与 DDS/SDK 网络分离。

MOCK 使用隔离的运行模式，不能访问真实机器人 IP。真实 ROS/SDK 场景按已验证配置决定是否使用 host 网络；不把 host 网络当万能解法，也不向所有网卡广播发现。

Web 服务默认 `127.0.0.1:8765`，不默认监听所有接口。采用一次性本地引导令牌建立会话，HttpOnly/SameSite cookie、写操作 CSRF、Host/Origin 允许列表。引导令牌不写日志，若用 URL fragment 传递，读取后立即清除。SSE 同样验证会话。

Docker 权限仅在主机上的受限执行器使用。运行账户有 Docker 访问权仍是高权限信任边界，必须按此威胁模型审查。禁止 Web 任意容器 API、任意挂载、任意命令、root SSH、整个 /dev 挂载、privileged 默认值。官方相关风险见来源 S19。

自动修复分级：缓存重试/项目目录创建可自动；依赖安装等宿主写操作需明确授权；机器人启动脚本/网卡/固件写操作不属于首版自动功能。机器人侧网络配置先生成可审查差异，保留原文件哈希与恢复方法；未经现场批准不执行。

## 9. 数据平面与导航范围（后续阶段）

上层契约使用标准 ROS 消息，但话题名不等于真实能力。`/imu`、`/odom`、`/joint_states`、`/scan` 或 `/points` 必须由真实、已校验的来源提供；缺失则标为不具备，不发布假值补齐。

里程计必须核实单位、坐标系、姿态顺序、时间戳和重置行为；同一 TF 边只允许一个发布者。目标关系是 `map → odom → base_link → sensor_frame`。仿真与回放显式启用模拟时钟；真机禁止误用回放时间。

最小导航任务选择室内平地 2D，不做台阶、攀爬、跳跃或运动中形态切换。先接入已确认的传感器数据，再选择 SLAM Toolbox＋Nav2；FAST-LIO/LIO-SAM 等是传感器专用扩展，不是无条件可切换的菜单。外参、时间同步和足够的点字段缺一不可。

Nav2 输出先接只读命令汇聚器/记录端；只有经现场验收的 D1 命令网关才可连厂商 SDK。点足和轮足不同姿态的 footprint/速度约束独立配置，不因 move() 有 vy 参数就启用全向控制。

## 10. 运动安全边界（不在 M0–M3 实现）

部署与运动是两套状态。首轮根本不实现 arm/运动 API。后续才设计 `DISARMED → ARMED_IDLE → ACTIVE` 和锁存故障态；服务重启、断线或配置变化一律撤销软件授权。

SDK 连接权由网关统一持有，导航和遥控只能经过它。需要命令有效期、单一控制源、幅值/变化率限制、遥测新鲜度、状态许可和退出路径。零速度、passive、lieDown 的效果不能凭名字推断，不把它们统称为安全急停。

上位机进程崩溃/网络中断时，它自身无法保证继续发送停止消息。必须核实并测试本体侧失联保护及独立物理遥控/急停途径，否则禁止启用运动。UNKNOWN 不能通过“我确认”变成已测安全。

不关闭厂商运控，不发低层力矩/关节控制，不从这个部署项目顺带开发步态 RL。

## 11. 阶段与完成定义

| 阶段 | 产物 | 通过后能说什么 |
|---|---|---|
| M0 | 源码来源/接口审计与真实版本锁 | 已核对来源，尚未部署 |
| M1 | Profile、Doctor、Resolver、Job Engine 单元测试 | 部署逻辑可测试 |
| M2 | 中文向导、CLI、明确标识 MOCK、报告 | 可运行演示产品，不代表 Docker/真机已部署 |
| M3 | 真 Docker 集成、CPU ROS 探针、安装包 | 软件部署链经过真实验证 |
| M4 | 一个准确型号/固件的 SDK 只读链 | 该组合的遥测已验证 |
| M5 | 真实传感器/地图/导航输出，只读命令 | 导航软件链已联通，未必能运动 |
| M6 | 有现场人员的安全/运动验收 | 仅对测试过的完整组合声称实机验证 |

完整验收见 [ACCEPTANCE.md](../../ACCEPTANCE.md)。后续里程碑细分见 [ROADMAP.md](../../ROADMAP.md)。本设计采用后，Codex 按第一阶段实施计划开始，不自动跨入下一轮。
